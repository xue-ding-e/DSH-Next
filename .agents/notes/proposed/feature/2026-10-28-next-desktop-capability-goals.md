# Agent Note: Next desktop capability goals

Status: proposed

English | [中文](2026-10-28-next-desktop-capability-goals.zh.md)

## Problem

The maintainer's 2026-10-28 request establishes thirteen long-running DSH-Next capability goals and interactive regression testing. Chat history alone loses acceptance details and unfinished work. Existing capability notes own individual mechanisms, not this combined product scope.

## Proposal

Keep this proposal as the durable goal and coverage register. Implement independent capabilities separately and update their rows with reviewed evidence; a new conversation, failed test, or unavailable platform does not close a goal. Preserve stable identifiers; expand G13 with linked, individually testable subgoals rather than silently replacing the original thirteen. This register does not assert that a capability is absent or already works.

### Survey before implementation

For each goal, first inspect configured plugin-market sources and existing shipped or experimental bundles. Record the source URL and retrieval date, package/version, license, maintenance and compatibility evidence, permissions, supported behavior, remaining gaps, and the reuse decision. An unavailable or empty market is a named discovery gap, not proof that no plugin exists. Do not add untrusted sources or install code merely to complete the survey. Reuse suitable maintained capabilities; implement uncovered behavior through documented extension points before considering core changes.

The [market decision](../../implemented/feature/2026-10-02-plugin-market-discover.md) describes an optional experimental market with no official default index. The [Session reference](../../implemented/architecture/2026-09-15-client-session-references.md), [explicit worktree](../../implemented/feature/2026-09-13-explicit-worktree-creation.md), [side-session](2026-07-08-interactive-side-sessions.md), and [desktop-update](2026-09-08-desktop-update-policy-and-installation.md) records retain their own decisions and verification requirements. This proposal neither supersedes them nor treats their existence as runtime acceptance evidence.

### Initial survey findings

On 2026-10-28, the [dsh-input-traffic market entry](https://dsh.pub/en/plugins/dsh-input-traffic/) lists version `0.2.9`. Its reorder candidate uses remove-and-resend reconstruction rather than an atomic queue reorder, and excludes image items. Static review identifies a concurrent-claim risk, not an observed runtime failure; this does not satisfy G05 without further verification. Preserve the exact inspected source revision in the linked evidence artifact.

The [official forge bundle](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.2-alpha.2/packages/experimental/forge-bundle/README.md) candidate is package version `0.2.2-alpha.2`, separate from B0. Its new-Session worktree/base-branch picker is a reuse candidate for G07, not evidence that B0 includes it or that it forks an existing chat into a worktree. Evaluate an independent adoption with original license and attribution retained; G12 still requires its own acceptance.

B0 already includes the [SQLite query implementation](../../../../packages/session-query/session-query-sqlite/README.md), while the [Web composition](../../../../packages/bundle/web-app/cordis.patch.yml) sets `openAt: never`. Assess index enablement, resource use, incremental refresh, cancellation and error feedback before adding another search engine. Its documented token/phrase matching is not arbitrary substring matching; agree and test G09's keyword semantics explicitly.

### Shared interactive acceptance matrix

Apply T to each goal and each applicable sub-action: normal, empty, loading, error, cancellation, repeated actions, keyboard/focus, Escape/outside-click, window resize and zoom, drag/drop, restart/persistence, and platform differences. Mark a dimension not applicable only with a reason. Record each case as pending, pass, fail, blocked or not applicable; untested and skipped cases never count as passed. G12's fork modes, unread state and notifications require separate results.

Use isolated synthetic workspaces/accounts and the supported desktop/web launch path. Combine focused unit/integration checks, relevant keyless snapshots, real interactive UI checks and actual desktop/OS integration where required; follow the owning [testing policy](../../../../docs/testing.md). For each execution, retain the command or reproducible steps, expected/actual result, timestamp, platform/app version and full tested SHA in the linked evidence artifact. Screenshots support visual inspection but never replace running the interaction. Record pre-fix failure, regression coverage, repair and post-fix rerun; then retest affected adjacent behavior.

The target is complete coverage of the enumerated capabilities and applicable UI states, not a promise of 100% bug freedom. Report case coverage, code coverage and supported-platform coverage separately, with their denominators and gaps; do not convert one percentage into another. A blocked OS or missing credential is an explicit pending result, not a pass. Reopen a previously accepted row when a regression or new supported platform invalidates its evidence.

### Safety and evidence ownership

Cross-Session operations require explicit, revocable authorization with a named discovery/read/invoke/notify scope, isolation between unauthorized Sessions, bounded forwarding/loop prevention, and deduplicated notifications. A Session reference or another Session's message does not grant authority. File actions validate and authorize targets through the owning host capability; never turn arbitrary displayed paths or Markdown into shell commands or widen filesystem permissions.

Use synthetic fixtures, not real conversation history, credentials or private project names. Keep private screenshots out of public repository files; sanitize evidence before publication and never record cookies, tokens or authentication headers. For G11, a missing release or manifest and its HTTP 404 are not evidence of token failure; establish repository, release, channel, platform and artifact availability before diagnosing authorization. Completion notifications remain subject to OS permission even when the app preference defaults on.

## Alternatives considered

**Keep the goals only in chat.** This loses scope and unverified cases across context changes, contrary to the explicit request for durable goals.

**Add a separate tracking framework or duplicate existing capability decisions.** Stable rows and evidence links fit the existing proposed-note lifecycle with less maintenance and no new tooling; mechanism details remain with their current owners.

**Implement everything in core or declare success from screenshots or a coverage percentage.** This skips reusable plugins and cannot demonstrate lifecycle, security or native integration behavior. Reuse decisions and executed acceptance evidence remain separate requirements.

## Acceptance criteria

- All thirteen goals retain their requested scope, stable identifiers, source, dependency/reuse decision, state, observable acceptance, uncovered cases, build/SHA evidence reference and test evidence.
- Before implementation, each goal records its plugin/source survey or a concrete blocker and identifies what existing capability can be reused.
- Accepted rows have executed evidence for T and their specific acceptance cases; defects are repaired and rerun, while incomplete platforms and unavailable services remain visible.
- Update both language files and their consistency record together. Keep this proposal open while any goal or derived subgoal lacks acceptance; when all are resolved, retain the rationale and evidence links and follow the existing implemented-note format rather than leaving an obsolete checklist.

## Risks

A long-running register can drift from shipped code; update the affected row with each implementation or regression and revalidate evidence against the tested revision. Plugin availability and comparison products can change, so dated public evidence is required and unavailable behavior remains unknown. Large UI state combinations need prioritization for execution, but prioritization must not erase uncovered cases or weaken authorization, privacy or platform checks.
